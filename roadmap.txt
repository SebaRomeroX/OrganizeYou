ORGANIZEYOU - PROJECT ROADMAP
=============================

WHAT THE PROJECT IS
-------------------
OrganizeYou is a personal organizer/reminder web app.
First iteration focuses exclusively on a to-do list.

WHAT WE'RE DOING AND HOW
-------------------------
- Keep the tech stack as simple as possible:
  HTML, CSS and vanilla JavaScript. No frameworks, no build tools,
  no external dependencies for now.
- Single-page app runnable by opening index.html in a browser.
- Data stored in the browser (localStorage) for now; a backend may
  be considered in later iterations.
- Mobile-first design: layout and styles are written for small
  screens first, then enhanced for larger screens with min-width
  media queries.
- Fixed dark theme UI: dark gray palette (no pure black), no theme
  toggle. Colors are defined as CSS variables in :root.

PROJECT GUIDANCE
----------------
- Prefer simplicity over abstraction: no over-engineering.
- Plain, readable code; small files; comments only where useful.
- UI decisions follow a mobile-first approach: design for the
  smallest screen first, scale up with breakpoints.
- Touch-friendly targets (buttons/list items >= 44px), viewport
  meta tag included.
- All decisions, changes and progress are registered in this file.
- Every completed task is checked off below and noted in the log.

SECOND GOAL: CATEGORIES & TAGS
------------------------------
Decisions:
- Categories are user-created and stored in localStorage
  (organizeyou.categories). A tag is simply a reference to a
  category, so tags and categories are the same list.
- Tasks gain a tags field (array of category ids); existing tasks
  migrate to an empty array (a task with no tags is valid).
- Task list is grouped: one section per category in creation order,
  a task with multiple tags appears in each matching section, and
  untagged tasks appear under "Uncategorized" at the end of the list.
- Page layout order: task input first, then categories input, then
  the grouped task list.
- Tags are assigned after creation via a + button that opens an
  inline picker of category chips to toggle on/off.
- Deleting a category removes it from all tasks (no confirmation).
- No filtering by category in this goal (kept minimal).
- Categories cannot be reordered yet (creation order).

FOURTH GOAL: REPETITIONS & SUBTASKS
------------------------------------
Decisions:
- Task modes are mutually exclusive: a task is either a normal
  task, a repetition task (counter like 2/5) or a subtask task.
- Repetition: ticking increments the counter, unticking decrements
  (floor 0); at target the task is auto-completed; unticking a
  completed repetition task resets to 0 (new cycle).
- Subtasks: the main checkbox is disabled; ticking subtasks
  controls the task; when every subtask is ticked the main task is
  auto-completed (and back to active if any is unticked).
- Subtasks are managed only in the new/edit task modal (min 1 to
  enter subtask mode). Enabling one mode clears the other.
- Data: task.repeats = { current, target } | null,
  task.subtasks = [{ id, text, done }]; existing tasks migrate to
  repeats: null, subtasks: [].

[x] 4. Task row UI: counter badge, subtask checklist rendering
[x] 5. Modal: repeat toggle + target input (new & edit)

FIFTH GOAL: CYCLES (RECURRING TASKS)
------------------------------------
Decisions:
- A cycle is orthogonal to the other modes: any task can have a
  cycle and it combines with counter repeats and subtasks (the
  repeat-vs-subtasks exclusivity is unchanged).
- Data: task.cycle = { every: N >= 1, unit: "hour"|"day"|"week"|
  "month", dueAt: timestamp | null }; migration adds cycle: null.
- Boundaries are calendar-aligned: every N hours from local
  midnight (2h -> 00, 02, 04...), every N days at local midnight,
  every N weeks on Monday, every N months on the 1st. For N > 1
  periods anchor to the epoch; N = 1 behaves as expected.
- When a cycle task becomes done (tick, counter at target, or all
  subtasks ticked) dueAt = next boundary after completion;
  unticking a done task clears dueAt.
- Reset: when now >= dueAt, the task goes back to active with
  progress cleared (counter 0, subtasks unchecked, dueAt null).
  Checked on page load and every 60s while the tab is open.
- Task row shows a static badge ("Every 2h", "Every day"), same
  family as the counter badge; no due/overdue highlight.
- Modal (new & edit): third block "Cycle" with checkbox toggle,
  number input (min 1) and unit select; default "1 day". Enabling
  it does not touch the repeat/subtask controls.

Tasks:
[x] 1. Data model: cycle field + migration for existing tasks
[x] 2. Calendar boundary helpers (hour/day/week/month, N>1 anchors)
[x] 3. dueAt on completion (tick, counter target, subtasks) + clear on untick
[x] 4. Reset engine: on load + every 60s while open
[x] 5. Modal: cycle toggle + every/unit controls (new & edit)

SIXTH GOAL: DISPLAY ORDER (PENDING FIRST)

- Sorting is display-only: localStorage keeps creation order and a

- Sort key is the done flag only, using a stable sort: pending
  tasks first (keeping relative creation order), done tasks last

- Tasks are sorted once per render, then filtered per group, so a
  multi-tagged task sits in the same relative spot in every
  section it appears in.
- No completion-time ordering among done tasks (kept minimal).
- No extra wiring for cycles: tick/untick and the automatic cycle
  reset already trigger render(), which re-sorts.

SEVENTH GOAL: COMBINED COUNTER + SUBTASKS
-----------------------------------------
Decisions:
- The repeat-vs-subtasks exclusivity is removed: a task can have
  repeats (counter) and subtasks at the same time.
- In a combined task completion is driven by the counter:
  done = counter >= target, no matter how many subtasks are left.
- Ticking a subtask increments the counter (+1, capped at target);
  unticking only unchecks the subtask - the counter never goes
  down from subtask ticks (this is what allows re-ticking to feed
  a target higher than the subtask count).
- Main checkbox in a combined task = standard counter behavior:
  enabled while active (click adds +1), click on the done task
  resets counter to 0 and unticks all subtasks.
- Modal suggestion: adding/removing a subtask sets the target
  input to the subtask count; a manually typed target sticks
  until the next subtask add/remove re-syncs it.
- Single-mode tasks keep today's behavior: subtask-only keeps the
  disabled main checkbox (complete when all ticked), counter-only
  unchanged. No migration needed.
- Resets: untick-done and cycle reset both clear counter AND all
  subtasks in combined tasks.
- Task row shows the 2/5 badge and the checklist together (name
  first, then cycle badge, then counter badge).

Tasks:
[x] 1. Remove exclusivity: modesToData returns both, repeat toggle keeps subtasks, Add subtask keeps repeat
[x] 2. toggleSubtask: increment counter (capped), combined completion rule, untick does not decrement
[x] 3. Main checkbox: click-to-add while active, full reset on untick-done
[x] 4. Modal auto-sync: target = subtask count on add/remove, manual edit wins
[x] 5. Reset paths: untick-done and cycle reset clear counter + subtasks
[x] 6. Edge cases (target clamping, badge + checklist together, single-mode unchanged)

EIGHTH GOAL: CYCLE TIMING (HOURS ELAPSED)
-----------------------------------------
Amends the fifth goal's hour decision; day/week/month keep their
calendar boundaries.
Decisions:
- Hour cycles are elapsed: dueAt = completion time + N hours
  (exact duration in ms). A 2h task ticked at 10:30 is due at
  12:30; ticked at 23:30 it is due at 01:30 the next day.
- True elapsed time: the ms addition also holds across DST
  changes ("2 hours must pass" taken literally).
- Day/week/month unchanged: next local midnight / next Monday /
  next 1st of the month (Goal 5 calendar anchoring stays).
- No migration: already-done hour tasks keep their stored
  calendar dueAt and reset once on it; everything after is
  elapsed. The migration fallback (done + dueAt null) becomes
  "completed now + N hours", which fits elapsed even better.
- Untick-clears-dueAt, the 60s reset engine, the badge text and
  the edit-recompute path are untouched - they just call the new
  hour math.

NINTH GOAL: CYCLE RESET ANCHOR (GLOBAL)
---------------------------------------
Decisions:
- One global anchor config defines where calendar cycles reset,
  applied to every day/week/month cycle task; hour cycles stay
  elapsed-from-completion (eighth goal) and are unaffected.
- Fields and defaults (= today's behavior, so old and new data
  behave identically): time "00:00" ("What time does the cycle
  start?"), weekStartDay Monday, monthStartDay 1, monthAnchor
  January. Stored in localStorage (organizeyou.cycleAnchor) with
  normalization: missing/invalid fields fall back to defaults.
- Per-task cycle data is untouched: no task migration.
- Boundary math: dueAt = smallest boundary instant > completion,
  where a boundary instant = boundary day at the anchor time:
  day = epoch dayNum = 0 (mod N); week = N-week periods starting
  on weekStartDay (epoch phase); month = months where
  (monthIdx - monthAnchor) = 0 (mod N) on monthStartDay. With
  default values this reduces exactly to the current formulas.
- UI: new Settings button in the header opens a "Cycle reset"
  modal (reusable Modal, modal.js unchanged) with four labeled
  controls; the time input's label is the message asking what
  time the cycle starts.
- On save: recompute dueAt of every done calendar-cycle task with
  the new anchor, then run resetDueCycles() so the change takes
  effect immediately (a cycle whose new start already passed
  resets on the spot).
- Time is built wall-clock via the Date constructor; DST-
  nonexistent times normalize (accepted edge). Badge unchanged.
- Month start day input is capped at 28 so it exists in every
  month.

Tasks:
[x] 1. Setting: load/normalize/save cycleAnchor with defaults
[x] 2. nextCycleBoundary: anchor-aware day/week/month (hour untouched)
[x] 3. Settings modal + header button + four labeled controls
[x] 4. Save: recompute pending dueAts + immediate reset check
[x] 5. Edge cases (strictly-after at exact anchor, 1-28 cap, DST time, invalid settings)
[x] 6. Regression: goal-8 harness passes with defaults + new anchor cases
[x] 7. Review and commit

TENTH GOAL: DEADLINE COUNTDOWN
-------------------------------
Decisions:
- Data: task.deadline is a string in one of two forms (migration
  adds deadline: null to old tasks): "YYYY-MM-DD" = date-only,
  counts to the END of that day; "YYYY-MM-DDTHH:mm" = with time,
  full countdown. null = no deadline. Past deadlines are allowed
  (badge shows overdue immediately).
- Input: new "Deadline" block in the task modal (same style as
  the Cycle block): a date input + an optional time input. Empty
  date = no deadline; date with empty time = date-only mode.
  Edit modal prefills; clearing the date clears the deadline.
- Wording (countdownInfo pure function -> { text, state }):
  date-only: "8 days" -> "1 day" -> "today" (whole deadline day)
  -> "overdue" next day. Timed: dateDiff >= 2 -> "N days"
  (calendar); >= 24h -> "1 day"; 60min <= left < 24h -> floor
  hours ("23 hours" ... "1 hour"); < 60min -> 10-minute floor
  ("50 min" ... "10 min", STAYS at "10 min" down to zero);
  past -> "overdue".
- Display: .countdown-badge in the task row after the cycle and
  counter badges; hidden when the task is done or has no
  deadline. States: normal (days) -> urgent (deadline day,
  hours, minutes) -> overdue (red).
- Live updates: the existing 60s tick re-patches badge
  text/class (no full re-render, keeps focus/scroll).
- Cycle reset: deadline left as-is; after an auto-reset the old
  deadline shows overdue until the user edits it.

Tasks:
[x] 1. Data: task.deadline + migration (deadline: null)
[x] 2. countdownInfo(deadline) for both modes (days/today/hours/10min/overdue)
[x] 3. Modal deadline block (date + optional time), new + edit + clear
[x] 4. Countdown badge in task row + styles (normal/urgent/overdue)
[x] 5. 60s tick: re-patch badges without full re-render
[x] 6. Edge cases (date-only today, exact boundaries, past/invalid input, done hides badge)
[x] 7. Regression: goal 7/8/9 harnesses + new countdown harness
[x] 8. Review and commit

ELEVENTH GOAL: APPOINTMENTS
---------------------------
Decisions:
- Concept: an appointment is the mirror of a deadline - the task
  must be completed AFTER that moment, so the task stays LOCKED
  until then.
- Data: task.appointment, same string forms as deadline (migration
  adds appointment: null): "YYYY-MM-DD" (date-only) or
  "YYYY-MM-DDTHH:mm" (timed). null = no appointment. Mutually
  exclusive with task.deadline - a task has at most one of the two.
- Lock: while now < appointment moment and the task is not done,
  the main checkbox, the subtask checkboxes and counter clicks are
  all disabled, with an explanatory aria-label. Unlock moment:
  date-only = 00:00 of that day (the whole day is the appointment
  day); timed = that exact moment. Editing/clearing the appointment
  in the modal unlocks early. A cycling task that auto-resets
  before its appointment locks again until the moment (accepted).
- Modal: two blocks side by side (Deadline and Appointment, same
  date + optional time inputs). Entering a date in one block
  auto-clears the other block's inputs and state; a hint line says
  they are mutually exclusive. Edit modal prefills the one in use.
- Wording (appointmentInfo pure function -> { text, state }),
  prefix "in" so the direction reads clearly: date-only:
  "in 8 days" -> "in 1 day", then at 00:00 of that day the badge
  becomes "now". Timed: "in 10 days" -> "in 1 day" (calendar) ->
  "in 23 hours" ... "in 1 hour" -> "in 50 min" ... "in 10 min"
  (10-minute floor), then at the moment "now". Once "now" it
  STAYS "now" (urgent) while the task is undone - never
  "overdue". Hidden when the task is done or no appointment.
- Display: .appointment-badge in the same slot as the countdown
  badge (after cycle and counter); since the two are mutually
  exclusive only one can ever show.
- Live updates: the existing 60s tick patches appointment badge
  text/class in place, and flips checkboxes back to enabled when a
  lock expires (no full re-render; full render only as fallback).

Tasks:
[x] 1. Data: task.appointment + migration (appointment: null)
[x] 2. appointmentInfo() both modes (in N days/hours/10min, then sticky "now")
[x] 3. Mutual exclusion: modal blocks auto-clear each other + hint
[x] 4. Lock: main checkbox, subtasks, counter disabled before the moment
[x] 5. Appointment badge in task row + styles (normal/urgent "now")
[x] 6. 60s tick: patch badges and unlock expired locks in place
[x] 7. Edge cases (00:00 boundary, exact moment, done hides badge, cycle re-lock, invalid input -> null)
[x] 8. Regression: countdown + goal 7/8/9 harnesses + new appointment harness
[x] 9. Review and commit

TWELFTH GOAL: TIME SINCE
-------------------------
Decisions:
- Concept: some tasks count how much time has passed since the
  last time they were done ("2 days since last time").
- Data: task.since, same string forms as deadline/appointment
  (migration adds since: null): "YYYY-MM-DD" (date-only) or
  "YYYY-MM-DDTHH:mm" (timed). null = no time-since mode. Fully
  independent of deadline and appointment - a task can have all
  three; the modal blocks do NOT clear each other.
- Date-only anchor = 00:00 of that day (same rule as appointment).
- Recording (auto + editable): completing the task sets
  since = now - a tick that turns done on, and a combined
  "done again" subtask click while already done. Unticking, the
  main reset and the cycle auto-reset KEEP the record (it is the
  history of the last completion). Counter-only intermediate
  ticks don't touch it. The modal can set/adjust the moment by
  hand ("Now" button fills the current minute); clearing the date
  turns the mode off.
- Wording (sinceInfo pure function -> { text, state }): counts
  UP, always state "normal" (never urgent/overdue), longest unit
  first: < 10 min "just now" -> 10-minute steps "10 min" ...
  "50 min" -> "1 hour" ... "23 hours" (both buckets only on the
  same calendar day) -> calendar-day diff >= 1: "1 day" ...
  "6 days" -> floor(days/7): "1 week" ... "4 weeks" (< 30 days)
  -> floor(days/30): "1 month" ... . A future moment clamps to
  "just now"; invalid input -> no badge.
- Display: .since-badge after the appointment badge, ALWAYS shown
  - even when the task is done (counting up from the last
  completion is the whole point of the concept).
- Live updates: the 60s tick gains refreshSinces() which patches
  badge text in place via dataset.since (no full re-render).

Tasks:
[x] 1. Data: task.since + migration (since: null, validDue reused)
[x] 2. sinceMoment() + sinceInfo() ladder (just now / 10 min / hours / days / weeks / months)
[x] 3. Completion hooks: toggleTask/toggleSubtask set since = now on completion events only
[x] 4. Modal "Time since" block: date + time + Now button, hint, edit prefill, clear = off
[x] 5. .since-badge always visible (done too) + neutral styles
[x] 6. 60s tick: refreshSinces() in-place patch
[x] 7. Edge cases (invalid -> null, date-only 00:00, untick/cycle keep record, future clamps to "just now")
[x] 8. Regression: new since harness + countdown/appointment/main_tick harnesses
[x] 9. Review and commit
